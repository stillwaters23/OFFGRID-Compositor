## How the co-pilots work

1. **Read everything, reading only.** Agents 01, 02, and 03 each read every repo doc listed above before starting. Reading about other features never means working on them.
2. **One feature at a time.** Each agent builds only its assigned Bootloader step, in its own lane.
3. **Review.** Agent 04, the HR Manager, reviews each finished step and returns PASS, FAIL, or BLOCKED, always with evidence.
4. **Viewer-side success code.** No step can PASS until Royalty confirms the one-time code seen on the viewer phone.
5. **Pause, then next.** After a PASS, the system says "pause," then the agents move on to the next task automatically. A FAIL goes back to the same agent until it's right.
6. **Agent scaling.** Only as many agents work as there are steps left. Two steps means two agents, one step means one agent, and the rest stay idle.

## 1. What OFFGRID-Compositor is

OFFGRID-Compositor is Royalty's private Android app, built for the Galaxy S25 Ultra and Galaxy A37 first, with a PC and OBS version later. It's installed directly on the phone, not through the Play Store. It mixes effects, overlays, voice, and a glowing terminal control panel into Royalty's **own outgoing video and audio**, so viewers on live and video-calling platforms see them. It also has a premium OFFGRID-to-OFFGRID calling lane, where both sides see everything.

## 3. Core design rule

- **Baked into the outgoing video:** every effect in a platform folder is drawn into the video Royalty sends. Nothing in a platform folder is local-only, because platforms draw their own chat and screens on each viewer's phone and OFFGRID can only change its own outgoing video.
- **If viewers can't see it on their phone, it's rejected.**
- **Each platform folder is its own lane,** holding only what that platform allows.
- **OFFGRID-to-OFFGRID** is the premium lane, where everything is visible to both sides.
- Private testing tools (feature 15 test toggles, feature 25 leak alerts, feature 37 results) are tools, not effects.

## 4. The agent system

- **Agents 01, 02, and 03** each build one feature at a time, only in their own lane.
- **Agent 04 is the HR Manager.** Agent 04 oversees Agents 01, 02, and 03 and reviews every step as **PASS**, **FAIL**, or **BLOCKED**, always with evidence.
- **Viewer-side success code (required before PASS):** Phone 1 (a dummy phone) runs the build, and Phone 2 is the viewer. Each test makes a one-time random number. On outside platforms it's burned into the outgoing video next to the effect, and in OFFGRID-to-OFFGRID calls it pops up natively. Royalty reads it on Phone 2 and enters it on Phone 1. There's no PASS without it.
- **Model fallback:** if Claude blocks a task, it's marked BLOCKED and logged. With Royalty's okay, the task moves to Grok under the same rules.
- Full rules are in `06 Prompts and Skills/Agent Lanes and HR Review.md`.

## 5. The Bootloader loop

1. **Read everything first, reading only.** Before any task, each agent reads all repo docs (Bootstrap, Bootloader, Agent Lanes and HR Review, Folder Guidance Panel, Terminal Plain Language Rule, Credentials Security Rule, Feature Scope, and everything in `02 Research`). Reading never means working on another feature.
2. **Royalty says go once** to start the loop.
3. **Build the assigned step** until it's right. A FAIL goes back to the same agent.
4. **Agent 04 reviews.**
5. **Pause.** After a PASS, the system says "pause," and Agent 04 logs the result in `05 Docs/Build Log.md`.
6. **Next task, automatically.** The agents get the next open steps without Royalty saying go each time.
7. **Agent scaling.** Only as many agents work as there are steps left. Two steps left means two agents, one step means one agent, and the rest stay idle.
8. **Repeat** until the system says "Build complete."

Royalty can say stop at any time. A BLOCKED step is logged to `07 Logs and Failures`, Royalty gets one plain line, and that step waits while the other lanes continue. Steps 0 to 29 are in `06 Prompts and Skills/Bootloader.md`.

## 6. Credentials rule (hard rule)

- No API keys, passwords, tokens, stream keys, or other credentials go in the repo, the chat, or any document.
- Credentials live only in Android's secure storage on the phone (the Android Keystore).
- If a key ever lands in the repo, treat it as burned: tell Royalty, log it without the value, and replace the key. Deleting the file doesn't remove it from git history.
- Any credential in the repo is an automatic FAIL in HR review.
- Never change the repository owner's email address or account email. Test only with dummy accounts, never the paid big-gifter account.
- The full rule is in `06 Prompts and Skills/Credentials Security Rule.md`.

## 7. Terminal Plain Language Rule

Everything the terminal says to Royalty uses simple words and short sentences, written for a 13-year-old who's new to the cyber world, with acronyms spelled out. For example, instead of "WebRTC leak detected," it says "Your real internet address is showing. Turn on Stealth mode now." Jargon is an automatic FAIL. See `06 Prompts and Skills/Terminal Plain Language Rule.md`.

## 9. Test result tracking (feature 37)

- A test toggle that passes the viewer-side success code is marked **"baked in as success."**
- A failed test is marked **"failed"** with a short plain-language note and flagged for more research.
- Royalty screenshots failed results and brings them back in a later session to review.
- It applies to every platform folder and never appears in the outgoing video.
